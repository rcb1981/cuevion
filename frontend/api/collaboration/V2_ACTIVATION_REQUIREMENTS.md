# Collaboration v2 activation requirements

Collaboration v2 is an inactive private-beta foundation. Its modules are not route-wired, must not be imported by the active frontend or active API routes, and must not be activated as part of security-foundation work.

## Phase 2A inactive HTTP adapter

The shared `api.collaboration.http_adapter` module now provides the import-safe transport boundary for future Collaboration v2 Python handlers. It is not a route, exposes no `handler`, and does not import application services. `CUEVION_COLLAB_V2_HTTP_MODE` remains fail-closed to `off`; no production route currently reads or activates it. Future route modules must evaluate their exact allowed mode before importing application services or reading a request body. They must preserve duplicate raw headers through `headers.raw_items()`, validate body framing and limits before `rfile.read`, and use the centralized public response and error serialization.

This Phase 2A slice activates no v1, v2, or frontend behavior. HTTP activation remains blocked on owner CSRF, atomic idempotency/recovery, durable rate limiting, missing owner and guest application services, retention approval, and production KV `EVAL`, Lua, response-shape, race, and TTL evidence.

Activation requires all of the following in a separate change and review:

- Set `CUEVION_APP_ORIGIN=https://app.cuevion.com` in production.
- Set `CUEVION_COLLAB_INDEX_HMAC_KEY` to a cryptographically random secret of at least 32 bytes, encoded as canonical unpadded base64url. There is no secretless fallback.
- During a controlled rotation only, set `CUEVION_COLLAB_INDEX_HMAC_KEY_PREVIOUS` to the former canonical key. New indexes use the current key; reads and creates validate both namespaces and atomically migrate valid previous-key pointers. Conflicts fail closed. Remove the previous key only after migration is complete and verified.
- Never reuse `MAILBOX_SECRET_ENCRYPTION_KEY` as either collaboration index key.
- Confirm that the production KV supports `EVAL`, the exact multi-key atomic semantics used by the production scripts, Lua `cjson`, TTL behavior, response shapes, and failure behavior. Matching Redis Cluster slots alone is not proof of production `EVAL` compatibility.
- Preserve the literal `{cuevion-collab-v2}` Redis Cluster hash tag on every v2 thread, source index, invitation, token index, per-thread invitation index, and guest-session key. The single-slot design is intentional for private beta; sharding requires a controlled data migration and a new review.
- Define and approve the retention policy before activation. The inactive foundation currently refreshes thread/source-index retention to 180 days and bounds invitation/session storage by their authored expirations (24 hours and 8 hours respectively). Legal, privacy, deletion, and operational retention requirements still require explicit approval.
- Reissue old v1 collaboration links. They must not be interpreted as v2 invitation or guest-session credentials.

Guest-session terminal states use a first-terminal-state-wins policy. An active session may become either `logged_out` or `revoked`; after that transition, its terminal status and audit timestamp are immutable. Owner invitation revocation still revokes the invitation but must preserve an already logged-out or revoked linked session. Logout must likewise preserve an already revoked session. Mixed terminal audit fields are malformed and must fail closed without writes or TTL refresh.

All guest-session clocks are monotonic. Every exchanged invitation graph requires the linked session `createdAt` to equal the invitation `exchangedAt`; Python bootstrap validation and every graph-consuming Lua mutation enforce that equality before any write. An update, CSRF rotation, logout, or revocation timestamp must be at least the session `createdAt`, `lastUsedAt`, and every applicable prior audit timestamp. A first terminal transition and a changed CSRF hash are non-idempotent and therefore require strict advancement beyond the applicable prior audit; equality is accepted only when returning an already-stored idempotent terminal result or performing a non-mutating read. Every mutation must retain the lesser of the current positive PTTL, the remaining absolute session lifetime, and the remaining linked-invitation lifetime; expired or nonpositive-TTL records are never revived.

Application records use exact Python integers. Redis JSON encodes every security-critical integer, including versions, timestamps, counts, revisions, and TTL inputs, as a canonical unsigned decimal string. Python wire decoders and Lua must reject JSON numeric tokens, signs, leading zeros, floats, exponents, booleans, and values greater than `2^53-1` before mutation.

The canonical Redis wire schema is closed and byte-bounded:

- Opaque collaboration, invitation, and message identifiers are case-sensitive ASCII `[A-Za-z0-9_-]{22,128}` strings. Mailbox identifiers are lowercase ASCII `[a-z0-9][a-z0-9._:-]{0,255}` strings. Hashes are exactly 64 lowercase hexadecimal characters, and email identities are already-canonical lowercase ASCII; wire-record validation never case-normalizes them into validity.
- Thread records contain exactly `v`, `collaborationId`, `ownerEmail`, `workspaceId`, `mailboxId`, `sourceRef`, `sourceMessage`, `state`, `messages`, `createdAt`, and `updatedAt`. Message objects contain exactly `id`, `authorKind`, `authorDisplayName`, `text`, `visibility`, and `createdAt`; `visibility` is required and never inferred on the wire. Google and custom-IMAP source-reference objects use their exact provider-specific field sets.
- Invitation records always contain the complete audit/state field set, including explicit-null `exchangedAt`, `revokedAt`, and `revokedBy` when those events have not occurred. `invitedEmail` is absent or a canonical email and never explicit null. `activeSessionHash` is absent until a successful exchange, is required for exchanged invitations and revoked invitations with `exchangeCount` one, and is never explicit null. A revocation actor is the exact canonical `ownerEmail`.
- Guest-session records contain exactly all 18 documented fields. `revokedAt` and `loggedOutAt` are required fields whose value is either canonical-null or the one status-appropriate canonical decimal timestamp; mixed terminal audits are invalid.
- Versions, thread/message millisecond timestamps, invitation/session second timestamps, exchange counts, and every script TTL/revision argument use canonical decimal strings on the Redis boundary. Typed Python conversion happens only after this wire validation. Raw records containing JSON number tokens, duplicate object fields, unknown fields, or malformed nested objects are invalid.
- Every string and aggregate wire-record limit is measured in the actual compact UTF-8 bytes in Python and Lua, without ASCII-escaping non-ASCII characters for size accounting. The principal limits are 128 bytes for opaque IDs, 256 for mailbox/display values, 512 for provider identifiers and sender values, 998 for subjects, 16,384 for message text and invitation/session records, 131,072 for source body text, and 262,144 for thread records. More restrictive field-specific limits still apply.

No route may accept dictionary-shaped or duck-typed authorization context. Internal operations require the resolver-minted opaque internal capability. Guest reads and guest mutations use distinct opaque capabilities; guest mutation routes must call `resolve_guest_v2_mutation_context` with the raw HTTP method and duplicate-preserving raw header pairs. Future route adapters must reject duplicate `Origin`, `Content-Type`, `X-Cuevion-CSRF`, and `Cookie` headers and must not collapse headers into a mapping first.

The deployed serverless root is `frontend/`. From that root the canonical inactive-v2 identity is `api.collaboration.<module>`, and canonical shared-helper identities are `api.user_config_store` and `api.inboxes.<module>`; `imap_connect_preview` is canonical only as a top-level module. Canonical package branches use package-relative sibling imports and do not mutate `sys.path`. Short-name loads of capability-bearing v2 modules fail with an import error. The protected v1 routes' historical `models` and `redis_store` imports are the only v2-module aliases, and each forwards in either import order to the exact `api.collaboration` module object without executing the business body twice. The documented active-v1 helper aliases are `user_config_store`, `mailbox_secret_store`, `authenticated_gmail`, `authenticated_imap`, `oauth_token_store`, and `fetch-gmail`; each likewise resolves to its exact canonical module object in either import order. `oauth_token_store` is included because the canonical Gmail helper and the active OAuth callback share its mutable storage/transport globals. No dotted alias for `imap_connect_preview` is supported. Arbitrary short or dotted aliases, including the former repository-root `frontend.api...` identities, are forbidden and fail before capability classes, sentinels, caches, or stores can be instantiated.

Import safety is tested in subprocesses whose working directory is exactly `frontend/`, with `PYTHONPATH` removed and the repository root absent from `sys.path`. The probes import every active Python API handler—including protected Collaboration v1 `thread.py` and `invite.py`, `download-attachment.py`, and `message-action.py`—in both relevant helper/handler orders, require no production secrets, and fail on attempted network, provider, or storage initialization. These import tests protect active v1 bootstrap compatibility only; Collaboration v2 remains inactive, and activation still requires the separate production KV `EVAL`, Lua `cjson`, response-shape, race, and TTL verification described above.

Security-sensitive `Cookie`, `Origin`, `Content-Type`, and `X-Cuevion-CSRF` values containing comma-combined representations must be rejected before cookie parsing or storage resolution. Raw guest cookies also reject any comma and leading or trailing whitespace.

Activation requires a separate read-only security review after route code exists, plus an explicit production KV compatibility test using the exact scripts and genuine competing clients. Do not infer activation approval from this inactive foundation or its local tests.
