## Result

A compact Collaboration header shows the subject, People count, Active/Resolved, one accessible Close action, and quiet source/lifecycle actions. The canonical timeline renders chat bubbles in its existing chronological order with individual activity IDs, refs, timestamps, focus targets and highlights intact. Own Shared bubbles use Cuevion pine; other users, guests, and ambiguous historical messages stay left. Internal notes have a private surface, lock icon and readable label. No grouping or avatars were added.

The only self-authority is:

```ts
entry.authorRole === "Cuevion user" &&
entry.authorUserId !== null &&
entry.authorUserId === currentCanonicalUserId
```

`currentCanonicalUserId` comes from `currentMemberUserId`, passed from `authenticatedUser?.userId ?? null`. There is no display-name, email, owner, participant-match or historical inference.

One visible composer defaults to Shared. Both drafts remain controlled by the existing separate WorkspaceShell state and unchanged send handlers. Switching modes never copies text. Each successful handler clears only its own draft. Retry retains the existing logical operation/key. Either in-flight send disables Send while the other draft can still be edited. Enter remains a newline. The privacy cue appears only in Internal mode.

People is closed by default and replaces the timeline within the existing scroll region when open. The access component remains mounted while hidden, preserving transient guest links and in-flight operations. New secure links reveal People automatically. Back to conversation closes People independently and returns keyboard focus to the trigger. Existing overlay close confirmation still applies when a secure link is retained, even with People hidden. Historic guest states remain available; active/pending guests contribute to the count.

View source email discloses the same source subject/sender/from/timestamp metadata as the previous Source email details. Resolve/Reopen use the same lifecycle handler and authority. Existing creation forms and underlying workflow values are unchanged. The established chat workspace shows no workflow jargon.

The composer sits outside the content scroll area. There is no new timer, polling, avatar request, background refresh, endpoint, websocket, SSE, optimistic message, message grouping or mailbox scan per bubble. Rendering is O(activity count). Notification opening closes presentation panels so the exact activity is visible; the display acknowledgement, focus/scroll sequence and mark-read ordering remain unchanged. No normal-open autoscroll was introduced.

## Fixture scope and replay

The local fixture extracts the actual Collaboration portal JSX, both owner send handlers, lifecycle handler, close-protection function, timestamp/error formatters and C3D display effect from WorkspaceShell at build time. It imports the real chat, access and owner API components/modules. Its API responses are in-memory fixtures; no application credentials, backend process or production route is used. Exact-mail selection is stubbed in the browser fixture and separately covered by the real notification-navigation and exact-message suites. The outer viewport wrapper and final close-confirmation shell are fixture scaffolding. Browser checks do not claim physical-device software-keyboard testing or a full live mailbox session.

Run from `/Users/rutger/cuevion-app` using already-installed dependencies:

```sh
node frontend/fixtures/collaboration-chat/build.mjs
node frontend/fixtures/collaboration-chat/serve.cjs
```

In another terminal:

```sh

./node_modules/.bin/tsc -p frontend/tsconfig.app.json --noEmit

```

The fixture serves only loopback `127.0.0.1:4175`. The browser runner blocks non-loopback traffic. `CUEVION_PLAYWRIGHT` and `CUEVION_CHROME` can point to another existing installation. No install command is needed. The generated bundle/CSS/HTML live in `/private/tmp/cuevion-c3p2a` and are not committed.
